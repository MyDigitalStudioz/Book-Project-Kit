# Page Polish — share, cache, and screenshot discipline for project pages

Harvested from Jon's wider site work (The Starting Blocks, Yolando's sites, the Hub) and applied to every book-project page — showcase, spread review, and any page that gets shared by link.

## Link previews must stay lean
- A page that will be shared (iMessage, Facebook, chat) keeps its HTML small with **images as separate files**. A single-file page with embedded images can pass 13 MB and link previews silently fail — no thumbnail, no card. (Learned on The Starting Blocks: splitting images took the page to 145 KB with byte-identical visuals.)
- og-image: 1200 × 630, and its URL is **versioned** (`?v=` stamp) so crawlers refetch instead of serving a cached card. Facebook caches aggressively — force a re-scrape via their debugger when a preview goes stale instead of changing the page again.
- Fold page weight + image splitting into the pre-publish check for every page.

## Cache-busting
- After any push, browsers and crawlers may serve stale assets. The standard fix: stamp `?v=YYYYMMDDHHMM` on the page's CSS/JS/image URLs inside the HTML before pushing, and hand out preview links with a fresh `?v=N` **only after** live byte-verification passes.
- GitHub's README image cache ignores same-path updates: after refreshing any repo image, bump the `?v=` stamp on its README URL.

## Screenshots stay current
- Whenever a build's visuals change, retake the screenshots in the same pass: README hero (dark mode), gallery views, og-image, and the repo social preview source. No stale screenshots, ever.
- Chat previews of images: downscaled JPEG (~1600 px, q88) with a FRESH filename — same-name re-sends render cached on iOS, and previews must preserve aspect (resize by width only).

## Publish verification
- Byte-verify live files against local after every push (md5). A Pages build can lag or stall behind rapid pushes — if verification fails 5+ minutes after a merge, push a nudge commit rather than polling.

## Showcase presentation (added 2026-11-20, kit v1.2.3 — the Book 2 showcase rules)
- **Cast cards lead with the portrait.** Every cast card (lead and supporting) shows the portrait first and carries a per-card **"Show full body" toggle** that reveals the full body below it, hidden by default — the full cast reads at one weight, and full bodies are one tap away, not absent. (Supersedes an earlier portrait-only round: full bodies live on the showcase behind the toggle, and in the cast files and cast book regardless.)
- **Place cards:** adopted environment plates get cards in the cast grid, after the cast (same card pattern — image, name, blurb — but **no full-body toggle**; they are places, not characters). Web media lives under `media/scenes/`, **square-cropped on each scene's signature elements** — choose the crop window per scene so the defining features survive (the Fireside plate's crop is taken from the side that keeps the lit fireplace, sofa, and rug); never blind-center-crop a wide plate.
- **Places graduate to their own section (amended 2026-11-20, kit v1.2.4):** the place-cards-in-the-grid step above is the interim home. Once a book's **full environment set is adopted**, the plates move into a dedicated showcase section of their own — **"The Places"** — at their native wide aspect with one-line blurbs, and **cast surfaces stay cast-only**: cast grids, cast decks, and cast flipbooks carry characters (and the extras sheet), never places. A place that was temporarily carded among the cast moves out at that trigger. Places are dashboard scenes, never census characters. Every place card/slide carries its reference code (REFERENCE-CODES.md).
- **A dozen sub-items present as ONE sideways deck, not a vertical stack (added 2026-11-20, kit v1.2.4):** a section of ~12 place cards stacked vertically eats ~12 screens for what are sub-items. Present the set as a **horizontal flip-through deck in the cast deck's own interaction family**: one plate centered at full section width, immediate neighbors peeking at the edges angled and dimmed (a gentler angle than the cast deck's — wide 3:2 scenery warps at the cast deck's full tilt), the deck's own arrows + position counter, swipe/drag navigation, keyboard arrows when focused, wrap-around at both ends, `prefers-reduced-motion` crossfades. No tap-to-flip (places have no backs). Result on Book 2: one screen tall instead of twelve.
- **Deck back-face lessons (added 2026-11-20, kit v1.2.4 — Jon's phone finds on the Book 2 cast deck):** (1) **The caption band always fits its content** — build the back face as a flex column and let the image area yield; nothing may hang below the name line where the card's edge can clip it (a half-cut "tap to flip back" hint is exactly the failure). (2) **Contained art on a flat fill shows hard edges** — behind the sharp contained image, lay an **ambient blurred twin of the same art** (cover-fit, blurred, slightly scaled to hide blur falloff) so the padding reads as a soft extension of the art itself; square art simply covers it. (3) **Prefer an icon over text for the flip hint** — a small gold circular badge with a return-arrow glyph, with a visually-hidden text label so the action stays accessible; visible hint text competes with the caption and clips.
- **Link rule: same-site = same tab, external = new tab.** Navigation among the project's own pages (showcase, bookshelf, spread review, dashboard) stays in the same tab; only genuinely external destinations (Drive, GitHub, Lulu, other sites) open new tabs. Probe invariant: the flipbook's static-anchor `target="_blank"` count is 0 (JS-set links to external stores are the sanctioned exception).
- **Menu:** the shared ☰ drawer's entry for the page you're on is marked in **gold** — gold = current page, on every surface.
- **Manuscript button:** the showcase footer carries a button — "Read the current manuscript — <Draft N>" — pointing at the author's current draft in Drive (external, so it opens a new tab). The label carries the draft version on purpose. **When a new draft is banked, re-point this button (target + version label) AND the dashboard's manuscript link in the same pass — never one without the other.**

## Page furniture patterns (added 2026-11-21, kit v1.2.5 — from Book 2's phone-review days)

- **One master footer on every page:** all pages of a multi-page site end with ONE footer band in the app-bar family — a near-black band a step darker than the page body, a hairline top border in the page's own line color, a gold letter-spaced wordmark + muted © line in the left cluster, muted produced-by + gold link in the right cluster; page-specific links slot into the right cluster. The band is full-bleed and flush to the page bottom; on phone the clusters stack. **Alignment rule:** the band's inner row matches the page's content column exactly — mind `box-sizing: border-box` when translating a padded column's max-width into the band's inner width (a padded wrap's max-width already includes its gutters). Version/build numbers live on the bookshelf app bar only; other footers stay clean, with no "Updated" stamp.
- **Artwork selectors are thumbnail filmstrips, not stacked pills:** when a selector's options have artwork, present them as ONE sideways-scrollable filmstrip (scroll-snap, hidden scrollbar) — a square thumb per option with its reference code as a chip on the thumb, its short name under it, the selected thumb wearing the current-state gold ring, and the selected thumb scrolling itself into view on tap. Pills cost a screen of vertical space; the strip costs one row and shows the art it selects.
  - **A fixed CSS size is not a size lock:** pin fixed-size thumbs in markup attributes AND min/max width/height CSS on the box itself, and prove equality by measuring rendered boxes in both engines — a stylesheet value can still lose to a device compositor.
  - **Measure the WHOLE item box, not just the image:** when a row "looks different sizes," the images are usually identical and the LABEL BLOCKS under them vary (a two-line name, a conditional microtext line). Equalize the item's full structure — reserve every conditional line at a fixed height (including an empty placeholder span on items that don't carry it) and top-align the columns — then prove it by measuring total item heights.
- **Frosted captions, ghost-proof neighbors:** on any deck or carousel whose cards sit on a translucent panel, neighbor text must never ghost through the active card. The active caption band gets a frosted-glass treatment (backdrop blur + saturate over a dark-enough gradient, a 1px top border in the page's line color, an inset top highlight) AND neighbor captions fade to near-invisible (opacity ≈ .08) with a slight blur. Dimming the neighbor slide alone is not enough: caption text at reading brightness survives dimming and collides with the active caption. Neighbor IMAGES keep their angled/dimmed treatment exactly — only their text is ghost-proofed.
- **The flip-card viewer pattern:** one object, two faces, tap to turn it over — the way to present anything that has a front and a back (a cover pair, a portrait / full-body pair). The front face shows by default; tapping (or Enter/Space) flips in place; navigation away resets every card to its front face. A drag past the navigation threshold navigates and never flips; `prefers-reduced-motion` swaps the faces instantly. The back face carries contained art over an ambient blurred twin of itself (see the deck back-face lessons above), never a crop.
  - **Flip-card chrome:** the flip badge lives on the FRONT face only — the back face carries no badge element at all. Never rely on `backface-visibility` alone to hide front-face chrome in the flipped state (some engines promote positioned chrome to its own layer, where it bleeds through mirrored): cull the turned-away face with a delayed `visibility` rule that lands when the flip transition ends and returns immediately on flip-back, scoped to no-preference motion so the reduced-motion crossfade is untouched.
  - **Hints are state-aware:** text under a flip card names the face you will see NEXT ("Tap the cover to see the back" on the front, "…the front" on the back), updated in the same pass that swaps the caption.
- **Deck arrows carry ONE locked style:** navigation arrows on every deck share a single style — a semi-transparent dark frosted circle with a gold chevron — identical in EVERY state: rest, hover, focus (focus may only ADD an outline ring), pressed, mid-transition. No state may change the fill or opacity, and no transition runs on the button. (The failure this prevents: a `:hover` wash sticks after a tap on touch screens, leaving the last-tapped arrow a pale ghost.)
- **A revealed set of large same-aspect images belongs in a snap strip,** not a vertical stack: one horizontal scroll-snap strip where each stop is one full item, with a scroll-tracked caption + counter under it (a throttled scroll listener picks the item nearest the strip's center — the strip IS the selector, no separate selector UI), prev/next arrows in the locked deck-arrow style clamping at the ends, and per-item status carried in the caption, not stacked cards.
- **Drawer nav tree + JUMPS EVERYWHERE:** on a long page, the shared drawer's space under the page links carries an on-page nav tree — one quiet row per section, in page order, labeled with the section's own header wording; sections carry `scroll-margin` so a sticky header never covers the title landed on. EVERY long page's drawer carries a tree of its OWN sections (never another page's), and grouped sub-panels earn their own stops so the jump lands on the panel asked for. **Every scroll a control triggers lands instantly** — nav-tree rows, back-to-top, on every page: cross-page-distance smooth rides on a long page read as lag. Internal strip/deck scrolling is unaffected.
- **Centering a scroll strip that fits:** a horizontal selector strip that should center when it fits is a shrink-to-fit box (`width: fit-content; max-width: 100%; margin-inline: auto`) with the scroll overflow kept — it centers on wide screens and degrades to the full-width scrolling strip on narrow ones, no media query.
- **The mobile pass (a standing checklist, run measured, not eyeballed):** at phone portrait AND landscape, in both engines — (1) document `scrollWidth == innerWidth` (no page-level horizontal overflow); (2) every image decodes after a full scroll-through; (3) every control ≥ 44px in its smaller dimension, or a documented exception (a locked design call, a plain body-text link); (4) no interactive-context text under 11px; (5) zero page errors; (6) core interactions exercised end-to-end (drawer, decks, flip cards, filmstrip, dropdowns, shelf → book → turn → shelf); (7) the standing locks re-measured, not assumed (arrow styles, thumb sizes, neighbor-caption opacity); (8) live md5 of every shipped file verified by clean single fetch. Chrome inside a locked viewer build that the owner has tuned is a measured observation, not a defect to fix unilaterally.
- **The cast lightbox walk:** a card grid whose items deserve a closer look (cast portraits, product cards) gets a **walk lightbox whose list is DERIVED FROM THE CARDS THEMSELVES** — name, caption, and images read from the DOM cards, never a second hand-maintained list, so the viewer can never drift from the page (add a card and it joins the walk). Tapping an item opens the lightbox ON THAT ITEM: the item large, its name and caption, a counter "N of M"; frosted edge arrows (the locked deck-arrow style) + swipe + keyboard walk the whole list **in page order, wrapping at both ends** — one continuous loop, no dead ends. A per-item variant toggle (portrait / full body) swaps the big image in place without moving the walk position, resets to the default variant on each walk step, and hides on items with no variant. Landscape follows the lightbox family's side-rail layout; close restores the exact scroll position. The cards themselves render unchanged — only the portrait gains button semantics; the card's own inline toggles must NOT open the lightbox.
  - **Companion rule — swipe surfaces kill native drags:** any image inside a swipe surface carries `draggable="false"` (plus `-webkit-user-drag: none; user-select: none`) and the swipe stage carries `touch-action: pan-y` — a native image drag fires `pointercancel` and kills the pointer walk before it starts.
